# Agent Note: 自适应的启动扫光播放

Status: implemented

[English](2026-08-27-adaptive-boot-reveal-playback.md) | 中文

## 问题

Web 启动页的品牌扫光动画把可见扫光位置直接映射到真实加载比率（已激活条目数除以总数）。客户端插件清单在几百毫秒内就能全部激活，于是 "DeepSeek Harness" 字标动画被压缩成一道闪光；而且挂载交接恰好落在最后一个插件激活的瞬间，把收尾的缓动直接掐断。固定延长启动时间虽然能解决闪光，却会让每次启动都显得缓慢，与机器真实的加载速度无关。

## 决策

`@deepseek-ai/dsh-client-web` 的 `BootPage` 会把整段扫光动画至少播放到导出的最小时长 `BOOT_REVEAL_MIN_MS`（1500 毫秒）。加载期间，扫光继续向真实的"已激活/总数"比率缓动，绝不在清单完成前提前报告完成。比率到达 1 之后，播放按"整段动画自页面构建起至少持续 `BOOT_REVEAL_MIN_MS`"推进剩余扫光：快速启动以成比例的更快节奏播完整段动画，慢于最小时长的启动本来就在跟随真实进度，最后一个条目激活后立即交接。

`AppWebEntry.run` 在条目激活与 UI 渲染器挂载之间等待 `BootPage.awaitReveal()`，因此应用接管挂载点之前动画总是播放完毕。此时插件树已经全部激活，等待只门控视觉交接，不影响就绪性。`awaitReveal` 在扫光完成、`fail()` 或 `dispose()` 时结算，因此失败报告与页面拆除绝不会被动画挡住。

播放循环用 16 毫秒的 `setTimeout` 心跳驱动，而不是 `requestAnimationFrame`：被遮挡的标签页不会执行 rAF 帧，会让后台刷新的页面永久停留在启动页；而基于时间的地板在被节流的定时器触发后会自行校正到正确位置。

## 备选方案

**固定延长启动等待。** 否决：无论真实加载多快，每次启动都要付出最坏情况的等待，这正是自适应节奏要避免的拖慢。

**立即挂载应用，把收尾动画叠加在其上。** 否决：ui-renderer 已经会对启动 DOM 做快照并水合，完成一帧交接；再加一层遮罩会重复 boot-page 对字标的所有权，却换不来任何就绪性收益——交接时插件树已经激活。

**保留 requestAnimationFrame 并给交接等待加超时上限。** 否决：上限定时器的回调是任何测试都无法到达的防御分支，会被按文件 100% 的覆盖率门槛拒绝；播放循环是 `setTimeout` 上的纯算术，在完成、失败或拆除时必然结算，不存在需要上限的真实卡死路径。

**只放慢现有缓动系数而不加时长地板。** 否决：纯缓动的时长仍取决于激活事件的到达节奏，突发式的快速启动依然会一闪而过，慢速时则无法预测地拖尾。

## 后果

快速启动在交接前最多付出 `BOOT_REVEAL_MIN_MS` 的额外视觉时间，而此时插件树已经激活；慢于最小时长的启动不付出任何额外代价。每次刷新都会看到完整的品牌扫光。boot-page 单测钉住无动画帧时的同步结算、失败与拆除结算，以及假定时器下的最小时长播放；boot 单测钉住挂载只在播放结算之后发生。
